## 1. The question, and the answer

[`2026-09-01-cdefd9d.md`](2026-09-01-cdefd9d.md) §9.2 measured that upstream's
head does not install on this fleet, and named the cause: `2d7f42b4f3`
vllm#52801 promoted `instanttensor` from `requirements/test/*`, where it carries
`platform_machine == "x86_64"`, into `requirements/cuda.txt` with no platform
marker, and every fleet device is aarch64. From that measurement the PINPORT
wave concluded that **no revision carrying `qwen4_exp` can be pinned on this
fleet**, because `2d7f42b4f3` (2026-08-19) is an ancestor of `e126687a9a`
(2026-08-31), the commit that registers the model.

The PINWINDOW wave ([#2589](https://github.com/mudler/vllm.cpp/issues/2589))
then measured, as a trailing probe in its own job, that `instanttensor 0.1.9`
**does** build from source on aarch64 once Python headers are present, and was
explicit that this did not overturn the conclusion:

```console
ITENSOR_NODEV_RC=1     # fatal error: Python.h: No such file or directory
APTDEV_RC=0            # apt-get install -y python3-dev
ITENSOR_DEV_RC=0       # Successfully installed instanttensor-0.1.9
```

Nobody had re-run the runtime-requirements install at a `qwen4_exp`-carrying
revision with the header package present, so the repair was a hypothesis and the
head's `RUNDEPS_RC=1` stood as the measurement. This wave runs it at the earliest
revision that serves the row.

### 5.3 `BUILDDEPS_RC=1` is this wave's instrument, not the target

```console
BUILDDEPS_RC=1
BUILDDEPS ERROR: Could not open requirements file: [Errno 2] No such file or directory: 'requirements/build.txt'
```

`requirements/build` is a **directory** in upstream and has been one since before
the pin; the file the job wanted is `requirements/build/cuda.txt`. So job A never
installed the build requirements, and every leg after `RUNDEPS` failed on one
line of that file:

```console
BUILD       ModuleNotFoundError: No module named 'setuptools_rust'
BUILD_RC=1
IMPORT ModuleNotFoundError: No module named 'vllm'
IMPORT_RC=1
EXT_RC=1
REG_RC=1
MODIMPORT_RC=1
```

`IMPORT`, `EXT`, `REG` and `MODIMPORT` all read `No module named 'vllm'`, which
is the signature of a package that was never installed rather than of a package
that does not work. **Job A therefore reports nothing at all about the
build-and-import half**, and this report does not read its reds as target
defects. That is the failure mode this row keeps paying for: an instrument whose
failure looks like a result. Job B installs `requirements/build/cuda.txt` and
answers that half.

`setuptools_scm` did run in job A, from the clone, and produced the shape the
`parity-pin` block requires:

```console

```

The `+g<sha>` segment prefixes `e126687a9a828d513c01a07cd69f025f27d63280`, so
`assert_oracle_commit` would be satisfiable at this target. **It is recorded and
NOT written into the block**, because the pin does not move and because a
